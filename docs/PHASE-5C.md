## 2. 为什么不复用 vault 那一套密码学

`vault.deriveSubkey` 是 HKDF，前提是输入**已经是**一段均匀随机的高熵密钥。
用户口令不是 —— 它低熵、可枚举，必须走带 salt 和工作因子的 KDF，
否则拿到包的人可以用字典每秒试几百万次。

也不能拿主密钥派生：那样导出的包**只有本机能解**，而「换机器 / 备份」正是
导出的用途。一个打不开的备份不叫备份。这条是动手前就定下的，见 HANDOFF §7。

**KDF 选 scrypt，不是因为它最好，是因为它是这台机器上唯一装得上的。**
Argon2 要编译原生模块，而这个环境没有 Visual Studio 构建工具（HANDOFF §3.1）。
`node:crypto` 自带 scrypt，零依赖。这个取舍和 SQLite 用 `node:sqlite`
而不是 better-sqlite3 同源。

参数 N=2^17、r=8、p=1（约 128 MiB、单次约 450ms，实测）。
参数写进包头，所以将来调大不会让旧包解不开。

## 3. 🔴 一条差点空过的 AAD 断言

包头 12 字节整个作为 AAD 参与 GCM 认证。第一版的断言是「把 `log2N` 从 8 改成 1，
应该打不开」，跑起来是绿的 —— 于是记了一句"AAD 生效了"。

**把 `setAAD` 整个删掉之后，20 条用例照样全绿。**

原因很简单，只是第一遍没想清楚：`log2N` / `r` / `p` **本来就参与密钥派生**，
改一个字节派生出的密钥就变了，GCM 自然通不过 —— 有没有 AAD 都一样。
那条断言够不着它声称要守的东西。

AAD 真正保护的是头里**不参与派生**的字段：`version` 和 9~11 三个保留字节。
改成两条新用例：

- 把 `version` 从 1 **降**到 0（`> PACKAGE_VERSION` 那道检查只拦往高改）；
- 翻掉一个保留字节（没有任何一处代码读它们）。

再删一次 `setAAD`，这两条立刻红，而 `log2N` 那条照旧绿 —— 红得对了。

今天 version 只有 1、保留字节还没启用，所以这是一道**为将来准备**的锁：
等格式演进到 v2、或者某个保留位开始表示"包体是压缩的"，降级攻击就是靠它拦的。
`log2N` 那条用例留着并改了名，因为「改参数打不开」本身仍然值得钉住，
只是它守的不是 AAD。

## 4. 🔴 导入只写中心记录，不碰磁盘

这是有意的收窄。导入若直接往磁盘写，就成了一条全新的、绕过 §6.4 的写盘路径 ——
而「任何外部修改在用户确认前都不能被覆盖」是这个应用最核心的禁令。

导入之后，用户走既有的「处理差异 → 以记录为准写回」把值落到磁盘，
那条路自带备份、并发校验和逐变量确认。**别为了省一步而在这里加写盘。**

合并语义是**只增不删**：包里有的补进来或更新，本机独有的变量不动。
所以导入不是"恢复到快照那一刻"——备份之后删掉的变量不会因为导入而回来。
界面上直说了，因为"以为恢复了其实没恢复"比"没恢复"更糟。

绑定关系**不自动重建**：目标机器上的项目和环境可能对不上，猜错一次就是把一把
Key 绑到错的文件上，而下一次同步会真的写下去。

## 5. 🔴 第二条差点空过的断言，和一次红得不对的实验

「导入之后磁盘上的 .env 一个字节都没变」——写完自我感觉良好，
直到把写盘 bug 放回去时才发现问题。

**第一版它跟着一次空操作跑**：包是从当前库导出的，原样导回去自然新增 0、更新 0。
什么都没导，磁盘当然不会变。断言绿着，但它什么都没验到。

改法是先用一条裸 SQL 把中心记录里某个值改掉，让这次导入**真的有事可做**
（更新 1 个变量），再比磁盘哈希。顺带加了一条「这次导入确实改了中心记录」
守着前提本身。

**而第一次注入的 bug 红得不对。** 我让 `applyImport` 往目标路径 append 一行，
结果那个路径的目录根本不存在，脚本直接 ENOENT 崩了 —— 验收报告上是
「脚本未抛异常」失败，而我那条断言压根没跑到。
改成先 `mkdirSync` 再写，两条断言才各自红出正确的信息。

**看的不能只是红没红，还得看红得对不对**（§8 那条教训的第三次应验）。

顺带修掉一处**说谎的失败信息**：那条断言的 detail 无论过没过都写
「N 个文件哈希未变」，红的时候那句话正好是反的。改成失败时列出被改动的文件。

## 6. 明确不做明文导出

规格 §7 只说「优先导出加密包」，并未禁止明文。这一刀选择不做：

- 明文导出是一条真正的明文出口，而用户已经有两条合法途径拿到值
  （逐变量 reveal 留痕、CLI 注入）；
- 一个"随手导出的明文文件"极容易被忘在下载目录里，
  而这个应用的其余部分花了很大力气避免明文落盘。

要做也该单独想清楚（二次确认、留痕、可能的自动清理），不搭在这一刀里。

## 7. 其它几条边界

**内容由主进程重新生成/解析，渲染层送不进来。** 导出请求里只有项目 id 和口令，
没有 payload；导入请求里只有路径、口令和选择集。让渲染层送内容进来，
等于给它开一个"往任意路径写任意字节"的原语。

**选包用专用通道，不是通用的「打开任意文件」。** `transfer:pickPackage`
顺带只读包头做一次识别，好在问口令**之前**就能说"这不是个导出包"。

**口令是渲染层 → 主进程方向的秘密。** 和明文出主进程是反方向：用户在界面上敲它，
主进程拿它派生密钥，它不进返回值、不进操作记录、不进任何日志。
`asPassphrase` 那个校验器里特意写了一句提醒：**绝不能把口令拼进错误信息** ——
`toFailure` 兜底那条 `console.error` 是全应用唯一会把原始异常整个打印出来的地方。

**凭据指纹不进包。** 它是 `HMAC(本机主密钥派生的子密钥, key)`，换台机器没有意义，
导入时用目标机器的子密钥重算。

**口令错和文件损坏分不出来，所以也不假装分得出来。** GCM 那里两者是同一种失败。
提示语两种可能都说 —— 谎报成"口令错误"会让用户对着一个已经损坏的备份反复试口令。

## 8. 验收

```
pnpm test         223 条单元测试（新增：包格式 22；222 通过 + 1 条按平台跳过）
pnpm verify:core  214 条（新增 14）
pnpm verify:ui    129 条（新增 8）
```

界面验收**不点导出确认**：那会弹一个原生保存对话框，CDP 点不掉，整个验收会挂到超时。
往返、口令、不落明文这些在 `verify:core` 里逐条验过；界面这一关验的是
「按下去之前」的那些守卫（没勾项目 / 没填口令 / 两次口令不一致都不放行，
以及三条都满足后**确实**放行 —— 少了最后这条，前三条可以靠"按钮永远禁用"蒙混过关）。

`preload 只暴露白名单方法` 按预期红了一次：40 → 45。
