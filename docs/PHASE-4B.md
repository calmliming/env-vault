## 2. 🔴 版本表里没有旧 Key 的密文

```sql
CREATE TABLE credential_versions (
  ..., fingerprint TEXT, last_four TEXT, created_at INTEGER, revoked_at INTEGER
);   -- 没有 encrypted_api_key 这一列
```

留着旧密钥是纯粹的负债。轮换的全部意义就是让旧的那把作废，
而一个"能翻出所有历史 Key 的数据库"会让**越勤于轮换、泄漏一次库文件的后果越严重** ——
那是完全反过来的激励。

只存指纹和末四位，它们回答了历史记录唯一该回答的问题：
**「我什么时候换的、换掉的是哪一把」**。指纹足以在别处（另一个项目、
一份旧备份）认出一把已经作废的 Key，而从指纹反推不回 Key 本身
（它是 HMAC，见 PHASE-3 §4）。

### `revoked_at` 记的是 Key 的世代，不是凭据的状态

只在**轮换**时写：这一代被下一代取代。用户按「停用」改的是
`model_credentials.status`，**不动版本行** —— 那把 Key 还是那把 Key，
只是这条凭据被搁置了。两件事混进一列，之后就再也分不开了。

### 存量凭据补一条 v1

迁移 005 用 `INSERT ... SELECT` 给已有凭据补出第一代。不补的话老数据的
历史是空的，界面上会显示成"从没轮换过"—— 而它只是没被记录过，那不一样。

⚠️ **这条补齐路径不在验收覆盖范围里**：验收每次都在全新的库上跑，
`model_credentials` 是空的，`INSERT ... SELECT` 一行也插不了。
验收里守的是它维持的那个**不变量**（「每条凭据都至少有一代记录」），
而不是补齐语句本身。写一条看起来在测补齐、其实够不着的断言，
比不写更糟（HANDOFF §8）。

## 3. 停用之后禁止同步和验证

「停用」是用户明确说过「这把不要了」。此后还把它写进 `.env` 文件、
或者拿去向厂商验证，都是在替他撤回那个决定。

守卫在 `credentials.ts` 的 `requireNotRevoked`，`syncCredential` 和
`validateCredential` 各调一次。界面同时禁用入口并说明原因 ——
和「归凭据管的变量不能就地编辑」同一个模式：
**界面挡是为了不把用户引到死路上，主进程挡才是规矩真正成立的地方。**

这个决定是可逆的：按钮变成「启用」，状态回到 `unverified`
（而不是回到停用前的 `active` —— 那次验证的结论已经隔了一段时间，
不该替用户宣布它仍然成立）。

## 4. 轮换前就摆出影响范围

原来的流程是「先换掉，再自己去点同步」—— 用户在按下确认那一刻
**并不知道这次改动会波及几个文件**。验收句要的正是这个。

`CredentialModal` 在轮换模式下挂载时调一次 `previewCredentialSync`，
把受影响的项目 / 环境 / 变量名列在确认按钮**上方**（界面验收里有一条
用 `compareDocumentPosition` 守着这个顺序 —— 摆在按钮下面等于没摆）。

🔴 **复用 `previewCredentialSync`，绝不另写一份影响范围计算。**
两份算法必然分叉，而分叉之后「到底会改哪几个文件」没有任何办法回答。
这里纯读：不勾选、不触发写盘，轮换本身依旧只改凭据。
预览同样只说改哪儿、不显示 Key —— 和同步预览同一条规矩。

## 5. 剪贴板

### 明文少过一次桥

复制原本是渲染层先调 `revealCredential` 把**明文取到渲染进程**，
再 `navigator.clipboard.writeText`。现在两个新通道只收一个 id，
主进程解密后直接写系统剪贴板，返回值里只有「多久之后会清」。

复制这条路上明文**完全不进渲染层**。「显示」那条路仍然必须过桥
（值要出现在屏幕上），复制不必 —— 这是两者的根本区别。

操作记录改记 `entry.copy` / `credential.copy`，不再复用 `*.reveal`：
复制和查看是两种不同的暴露方式，审计时要分得开 ——
**复制出去的那一份会离开本应用**，而查看不会。操作记录页上这两类都标橙色。

### 🔴 只清理我们写进去的那一份

30 秒后无条件 `clear()` 是个陷阱：用户很可能在这期间复制了别的东西
（一段代码、一个网址、另一个密码），那样会**把他的剪贴板毁掉**。
一个安全功能顺手破坏用户数据，比不做这个功能更糟。

所以写入时记下值的 sha256，到点先读回来比对，一致才清。
读不到剪贴板时也不清 —— 清一个不知道是什么的东西比不清更糟。

🔴 记哈希而不是明文副本：值已经躺在系统剪贴板里了，
没有任何理由在自己进程内存里再存一份，那只是多一个会被崩溃转储捞出来的地方。

连续复制两次只留最后一个定时器。不取消上一个的话，第一个到点时拿旧哈希
去比对必然对不上，于是什么也不清 —— 「30 秒后清理」会在连续复制时**静默失效**。

### ⚠️ Electron 44 的剪贴板 API 全是异步的

没有同步版本。这直接影响退出时的清理：`before-quit` 不会等 Promise，
fire-and-forget 的话进程先没了，清理根本来不及跑 —— 等于写了一个不生效的
安全措施。所以 `main/index.ts` 里要**拦一下退出**，两道保险避免
「清不掉剪贴板」变成「应用退不出去」：

1. 只有真有待清理的东西时才拦（`hasPending()`）；
2. 最多等 300ms —— 清剪贴板重要，但没重要到值得让用户面对一个卡住的窗口。

标志位在发起异步之前就置上，所以第二次 `before-quit` 直接放行。

### 30 秒写死为常量

计划 §7 说「默认 30 秒」，"默认"意味着可配置，但这个应用还没有任何设置
持久层（设置页目前是只读诊断）。为一个数字铺一整套设置存储不划算，留给以后。
toast 里如实说明秒数，用户至少知道会发生什么。

### 🔴 把 bug 放回去，三次都红了

- **清理不比对哈希直接清** → 两条断言红（定时清理那条 + 退出清理那条）；
- **版本表塞一列明文** → **两条独立的断言同时红**：逐列扫描报出
  `泄漏的列: leaked_key`，整库字节扫描也命中了那几把 Key。
  两条互相独立是有意的 —— 前者说得出是哪一列，后者连没想到的地方也扫得到；
- **停用不再拦同步** → 那条拦截断言红（`code=` 空，说明根本没抛）。

顺带确认了「版本表里没有存密文的列」那条**没有**红 —— 因为我把泄漏的列
起名叫 `leaked_key` 而不是 `encrypted_*`。这是对的：那条守的是命名，
真正兜住内容的是逐列扫描。两条各守各的，别指望其中一条替另一条工作。

### 顺手修掉一条会随机变红的断言

阶段 3 留下的 `!fingerprint.includes('cdef')`（Key 的末四位）是一条
**会随机失败**的断言：指纹本身就是 16 位十六进制，而 `cdef` 也是合法的
十六进制串 —— 偶然出现的概率约 1/5000，而每次跑沙箱主密钥都不同、指纹跟着变。
这一刀实测撞上了一次（`790e48a7cdef059c`）。

更要紧的是**那样测没有意义**：十六进制串里出现四个十六进制字符说明不了任何事。
换成两条确定性的：Key 里**非十六进制**的片段不该出现（真出现就是拼接了原值），
以及 🔴 **指纹不等于裸 SHA-256** —— 后者才是 PHASE-3 §4 的全部理由所在
（裸哈希会让拿到库文件的人能拿候选 Key 字典比对，派生之后没有系统密钥库
就什么都验证不了）。

### 一条断言接连两次拦住了新动作

阶段 3 加的「记录里的动作都是中文」那条，这一刀又红了一次 ——
`entry.copy` / `credential.copy` 新增之后忘了配标签。
这类**会因为新增而变红**的断言值得多写：它们把「加东西时顺手过一眼」
从自觉变成了机制。`risk.test.ts` 里那条「入参里没有放值的字段」是同一个用法。
