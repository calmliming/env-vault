# 阶段 6：一次纳管多个项目

不在 `DEVELOPMENT_PLAN.md` 的原计划里。做它是因为它**不是功能缺失，是正确性缺陷**。

前置记录：[PHASE-0.md](PHASE-0.md) ~ [PHASE-5C.md](PHASE-5C.md)。

## 2. 🔴 修的是什么缺陷

`projects.git_root` 一个项目只存**一个**，`db/security.ts` 拿它做全部 Git 判断。

把 `~/code`（底下十几个仓库）当成一个项目纳管，有两种坏结果：

1. `~/code` 不在任何仓库里 → `gitRoot` 为 null → 安全检查整页「查不了」。
   这个至少是**吵**的，按 PHASE-4A 的规矩 `unknown ≠ ok`。
2. **`~/code` 自己也是个仓库** → 所有 `git ls-files` / `check-ignore` 对着**外层**
   仓库问，而嵌套仓库里的文件在外层看来一律「未跟踪」。

第 2 种是做这一刀的理由。把 bug 放回去时验收脚本给出了它的精确形状：

```
FAIL  🔴「已提交又补进 .gitignore」在子仓库里照样报得出来
      —— level=ok tracked=false ignored=true
```

`tracked=false` + `ignored=true` 在判定表里是「已忽略且未跟踪 → ok，这是我们
希望看到的状态」。也就是说：**一个已经提交进仓库的 Key，被判成了安全。**

不是报错，是判成安全。这正是这个工具存在的理由被反过来用了。

## 3. 设计：一个项目 = 一个仓库

考虑过让一个项目跨多个仓库（`env_files` 加 `git_root` 列、`security.ts` 按仓库
分组）。否掉了：那要动数据模型和安全检查这块所有东西脚下的地基，
换来的是一个没人想要的心智模型 —— 「把 15 个仓库当成一个项目」不是用户脑子里的东西。

现在的做法只是**批量发现**：选中的目录是个入口，不是实体。发现 N 个仓库根，
建 N 条项目记录。`security.ts`、`risk.ts`、监听、差异、写回、排除项**一行都没改**。

## 4. 🔴 发现和扫描必须分两阶段

直觉写法是「深扫一遍再按 `.git` 归组」，但 `scanProject` 的限额是**按单项目**定的
（`maxDepth: 6` / `maxFiles: 200`）。一次深扫十几个仓库，深度预算会被父目录那一层
吃掉；200 个文件也可能在扫到第 8 个仓库时触顶 —— 而 `walk()` 是**先文件后目录**，
触顶时后面的仓库会被整个丢掉，用户只看到「少了几个」。

所以 `discover.ts` 只找 `.git`、**不读任何文件**，然后对每个仓库根各自调用
`scanProject`，各自享用完整预算。

## 5. 🔴 扫描侧也要在嵌套仓库处停

光有发现不够。`scanProject(repoRoot)` 原本会一路钻进子模块，把它们的 `.env`
收进父项目 —— 那些文件仍然会拿**父仓库**的 gitRoot 去判断，缺陷原样保留。

所以 `walk()` 现在遇到含 `.git` 的子目录就停，并把它记进 `ScanResult.nestedRepos`
让界面如实说出来（"这几个仓库要单独纳管"，而不是让用户以为扫漏了）。

⚠️ 这是一处**行为变化**：以前子模块里的 `.env` 会被收进父项目，现在不会了。
这是正确的收窄 —— 它们本来就该作为独立项目纳管，而发现功能正好会把它们列出来。

## 6. 一个中途改掉的设计

第一版是「指着一个仓库就只给这一个，不展开子模块」，理由是"意图很明确"。
写完才发现它让**最常见的一种布局用不上这个功能**：`~/code` 自己也 git init 过、
底下放着一堆 clone —— 那时一个都批量不了，而这恰恰是缺陷最容易发生的场景。

改成：选中目录自己是仓库时，它也算一个项目，但**仍然往下找**。

## 7. 其它几条

**批量导入是逐项目一个事务，不是一个大事务。** 撞到一个已经纳管过的路径不该让
另外十几个一起失败 —— 那会逼用户去猜"到底哪个出了问题"。跳过的逐个报出来。

**逐个走同一道路径校验。** 批量不是放宽 IPC 入参校验的理由。

**添加弹窗一个入口两种形态**：发现 1 个 → 和以前一样（带项目名输入框）；
发现多个 → 逐个列出，项目级和文件级两层勾选。

## 8. 验收

```
pnpm test         234 条单元测试（新增：发现 11；233 通过 + 1 条按平台跳过）
pnpm verify:core  221 条（新增 7）
pnpm verify:ui    129 条（preload 白名单 45 → 47）
```

`verify:core` 单独造了一个 workspace fixture（自己是仓库 + 底下两个独立仓库），
**没动现有的 fixtureRoot** —— 样例数据是共享的，往里加仓库会弄红一堆按数量
写死的断言（§8 那条教训）。

守着这一刀的核心是两条：

- 每个项目的 `gitRoot` 是**它自己**的仓库根；
- 「已提交又补进 .gitignore」那条 critical 在**子仓库自己的**报告里照样报得出来。

把 bug 放回去（让 `findGitRoot` 返回最外层仓库而不是最近的）时两条都红，
而且红出了缺陷的精确形状（见 §2）。这个注入方式是故意挑的：它精确复现
"问错仓库"，而不是随便造一个失败。
