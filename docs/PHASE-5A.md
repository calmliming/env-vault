# 阶段 5a：CLI 注入（`envvault run`）

对应 `DEVELOPMENT_PLAN.md` §9「阶段 5」的第一项与它的验收句：

> CLI 注入模式可以在不落盘明文 Key 的情况下启动本地开发命令

前置记录：[PHASE-0.md](PHASE-0.md) ~ [PHASE-4B.md](PHASE-4B.md)。

## 1. 这一刀交付了什么

| 内容 | 状态 | 落在哪 |
| --- | --- | --- |
| `envvault run -- <命令>` 参数解析 | ✅ | `src/main/cli/args.ts`，19 条单元测试 |
| 解析一个环境的全部变量（含凭据覆盖） | ✅ | `src/main/db/inject.ts` |
| 起子进程、转发信号、传出退出码 | ✅ | `src/main/cli/index.ts` |
| 无窗口模式下解锁 Vault | ✅ | `main/index.ts` 在单实例锁**之前**分支 |
| 生成 `.env.example` / 加密导出 / 外部 Secret Manager | ⬜ 5b 及以后 | 见 §7 |

## 2. 三件先摸清楚的事

**CLI 必须跑在 Electron 里。** 主密钥是用 Electron 的 `safeStorage` 封的
（`security/keystore.ts`），纯 Node 进程解不开。所以 CLI 是同一个应用的
另一种启动模式，不是一个独立的 node 脚本。

**解锁不需要窗口。** `vault.unlock()` 只读密钥文件 + 系统密钥库。
交接文档里我原先把这条写成了「阶段 5 的难点」——**那是高估了**：
`verify-core.ts` 从阶段 0 起就是无窗口跑 Electron 并解锁的，路早就通了。

**真正的坑是单实例锁。** `main/index.ts` 里取不到锁就 `app.quit()`。
用户开着界面再在终端里跑 `envvault run` 是最正常的用法，
被锁挡下来的表现是「命令莫名其妙什么也没做就退出了」，**而且退出码是 0**——
脚本里根本看不出出过事。所以 CLI 分支必须走在取锁之前。

不取锁是安全的：CLI 只读数据库（外加一条注入记录），WAL + `busy_timeout`
已经处理了并发。真正需要独占的是「两个主进程同时写同一个 vault.key」，而 CLI 不写它。

## 3. 🔴 不落盘，但这不等于隔离

值只经 `spawn` 的 `env` 传给子进程。没有临时文件、没有 `.env` 副本。
验收里有一条断言在一次**成功的**注入前后各扫一遍沙箱和系统临时目录，
确认没有多出任何含那把 Key 的文件。

但环境变量在多数系统上对**同一用户的其它进程**可见
（Linux 的 `/proc/<pid>/environ`、Windows 上的进程查看工具）。
帮助文本里把这一点直说了，单元测试也钉住了那几句话在不在：

> 「不落盘」和「完全隔离」是两件事，在共享机器上请据此判断。

和「厂商验证不代表 Key 一定可用」、「`unknown` 不是 `ok`」是同一种诚实。
一个密钥工具最不该做的事，就是让用户以为自己比实际更安全。

## 4. 🔴 `resolveEnvironment` 绝不能上 IPC

这个函数一次返回一个环境里**所有**变量的明文。

逐变量 reveal 的审计（每次调用留一条记录、界面上要点一下才显示）存在的
全部意义，就是不让这种批量读取悄悄发生。它对 CLI 进程是必要的 ——
子进程要的就是这些值 —— 但一旦出现在 `shared/ipc.ts` 里，
渲染层就能一次性拿走整个环境的明文，前面几刀在明文边界上做的功夫全部作废。

调用方只有一个：`cli/index.ts`，它跑在一个没有窗口、没有注册任何 IPC
处理器的进程里。

一次注入记**一条** `cli.inject`，detail 里是变量名和条数。逐变量记会把
审计日志淹掉，而这一次注入本来就是一个动作。操作记录页上它标橙色 ——
注入把一整个环境的明文交给了另一个程序，比复制走得更远。

## 5. 🔴 绑定到凭据的变量取凭据的当前值

与阶段 3「真源只能有一个」一致：凭据就是那把 Key 的真源。

一把刚轮换、还没同步回文件的凭据，如果按文件里的旧值启动开发命令，
用户会看着界面上明明已经换过的 Key，却怎么也想不通服务为什么还在用旧的。

代价是注入的值可能和磁盘文件不一致，所以 CLI 启动时会把
「哪些变量来自凭据、其中哪些和文件不一致」列出来（**只列变量名**）。

已停用的凭据**不注入**，和「停用后拒绝同步」同一条规矩：
用户说过这把不要了，那就不该再被塞进一个正在跑的进程里。

## 6. Windows 上的参数不能交给 shell

`npm` / `pnpm` 在 Windows 上是 `.cmd` 脚本，`spawn` 不开 shell 起不来
（Node 18.20+ 起还因为 CVE-2024-27980 明确拒绝）。但一旦开了 shell，
cmd.exe 会**重新解析**所有参数 —— `node -e "if (a) …"` 里的引号和括号
就被搅乱了，而且是静默的，用户只会觉得"我的脚本怎么突然语法错误了"。

折中：`resolveExecutable` 按 PATH + PATHEXT 找出命令对应的真实文件，
只有确实是 `.cmd` / `.bat` 时才显式起 `cmd.exe /d /s /c`
（`/d` 跳过 AutoRun，别让用户机器上的注册表项掺进来），
参数照旧逐个交给 `spawn`，不拼命令行。其余情况完全不经过 shell。

⚠️ 已知边界：传给 `.cmd` 的参数里如果嵌了双引号，cmd 的引号规则和 Node 的
转义规则对不齐，仍可能走样。真遇到时在 `--` 后面自己写 `cmd /c ...`。

其余两条也值得记：**输出全部走 stderr**（污染子进程的 stdout 会让管道和
`$(…)` 都坏掉）；**转发 SIGINT / SIGTERM**（父进程先死会把子进程变成孤儿，
用户按了 Ctrl+C 却发现 dev server 还在后台跑）。

## 7. 明确没做的

- **`.env.example` 生成**（5b）。`document.formatSkeleton` 已经能产出
  不含值的骨架 —— 那正是这件事要的东西，别重写。
- **批量导入与加密导出**（5b）。计划 §7：导出要二次确认、优先导出加密包。
- **1Password / Bitwarden / Doppler 适配**。它们需要机器上装有各自的 CLI，
  验收里只能全程用假的 —— 而一个只验过假实现的集成等于没验。单独再议。
- **把 `envvault` 装进 PATH** 是发布时的事（electron-builder 的安装器）。
  现在打包后是 `EnvVault.exe run -- <命令>`，开发期是
  `electron . run --project fixture --env local -- node -v`。

## 8. 验收

```
pnpm test         180 条单元测试（新增：CLI 参数解析 19）
pnpm verify:core  187 条
pnpm verify:ui    113 条（端到端的 CLI 在这里，理由见下）
```

### 端到端为什么在 verify-ui 而不是 verify-core

独立跑 `pnpm verify:core` 时没有 `--user-data-dir` 开关，于是走
`app.setPath('userData', sandbox)` —— 而 Windows 上 safeStorage 的 OSCrypt
密钥存在**Chromium 启动早期就定下的**那个 userData 的 `Local State` 里，
`setPath` 改不动它。结果是：数据库在沙箱里，解 vault.key 的密钥在默认
userData 里，两者分开。子进程无论用哪个 userData 都凑不齐这两样。

`verify-ui.mjs` 那边两个进程都带着同一个 `--user-data-dir`，所以端到端
只能放在那儿。顺带它还多验到一件事：**那时界面正开着**，
CLI 照样跑得起来 —— 单实例锁那条真的被绕开了。

> 🔴 第一版把端到端写在 verify-core 里，结果 CLI 根本没起来，
> 而「磁盘上搜不到 Key」那条却 **PASS 了** —— 它是空过的。
> 断言够不着它要守的分支时，看起来和真的通过一模一样。

### 🔴 「不落盘」用前后快照，不用白名单

第一版是「扫出所有含这把 Key 的文件，再排掉 fixture 目录」—— 错的：
备份目录（写盘时自动建的）里本来也有这把 Key，于是误报。
更糟的是白名单这个思路本身会越加越长，最后把真正的泄漏也一起放过。

改成在一次成功的注入**前后各扫一遍**，比较集合是否增长。
这直接回答了要问的那个问题：这次运行有没有让磁盘上多出一份。

### 🔴 一次空的「把 bug 放回去」

三条实验里，头两条正常变红。第三条（吞掉子进程退出码）**却是绿的**——
差一点就当成"这条断言没用"记下来了。

真正的原因是：改完之后 `pnpm run build` **失败了**（改动留下一个未使用的
变量，`noUnusedLocals` 报错），而我把构建输出重定向掉了没看见。
于是 `out/main/index.js` 还是旧的，被测的根本不是带 bug 的那份代码。

换一种不产生未使用变量的改法、并**先确认构建真的成功**之后，那条断言立刻红了。

教训比断言本身更值钱：**把 bug 放回去之后，先确认它真的进了被测的产物。**
构建失败 + 旧产物 = 一次什么都没验到的实验，而它和"断言无效"在结果上
长得一模一样。别把构建输出重定向到 `/dev/null`。

### ⚠️ 单独跑 verify:core 或 verify:ui 前要先 build

CLI 的端到端走的是 `electron .` → `package.json` 的 main → `out/main/index.js`，
那是 `pnpm build` 的产物。`pnpm verify` 的顺序（test → build → verify:core →
verify:ui）本来就是对的，但**单独跑**其中一步时要自己保证产物是新的。

这和 HANDOFF §2 里那条「`verify:ui` 跑的是 `verify:core` 那步生成的包」
是同一类坑，现在有两个了。
