## 2. 为什么是问 git，而不是自己解析 .gitignore

自己实现忽略规则要处理否定模式、`**`、目录尾斜杠、嵌套 `.gitignore` 之间的
优先级、`.git/info/exclude`、`core.excludesFile`……

写错的后果不是漏报，是**假的安心**：告诉用户「这个文件已经被忽略了」而实际上没有。
对一个安全检查功能来说，这是最坏的一种错 —— 用户会拿着这句话去决定要不要提交。

`git check-ignore -v` 直接给出权威答案，还顺带告诉你是哪一条规则命中的。

## 3. 🔴 `--no-index`：整个功能能不能成立就看它

```
git check-ignore -z --verbose --no-index --stdin
                              ^^^^^^^^^^
```

`git check-ignore` **默认不会**把已跟踪的文件报成 ignored —— 因为对 git 来说，
已跟踪的文件本来就不受忽略规则管。而我们要问的恰恰是另一个问题：
**「这个文件写没写在 .gitignore 里」**。

少了这个开关，「已经在 .gitignore 里、但仍然被跟踪着」这个最该报出来的情况
就永远检测不到 —— 它会安静地显示成「没有被忽略」。

### 而那正是最有价值的一条结论

```
tracked && ignored → critical
```

真实世界里的顺序几乎总是「先提交了 `.env`，后来才想起来加进 `.gitignore`」。
加完之后 `git status` 变干净了，于是所有人都以为堵上了 ——
而那把 Key 还在仓库里躺着，并且还会跟着每一次 push 出去。

**`.gitignore` 不会让已经跟踪的文件脱管。** 处置办法必须是
`git rm --cached`，而不是「加进 .gitignore」—— 后者正是用户已经做过、
并且以为已经解决了的事。提示语里还要说明：这不会删掉已经进入提交历史的
旧版本，泄漏过的 Key 仍然要作废重发。

## 4. 🔴 两条产品判断

**一、不喊狼来了。** 「被跟踪」本身不是罪：一个不含任何敏感值的 `.env.example`
进仓库是完全正常的做法。一个在每个项目上都把它标红的安全页，用户看两次就
再也不看了 —— 之后真出事那次他也不会看。定罪的是「被跟踪**且**里面有东西」。

模板不豁免高危值：`.env.example` 里塞了真 Key 仍然是 critical
（`classify.ts` 已有一条测试守着「公开前缀里塞了真 Key 依然要报出来」）。

**二、`unknown` 不是 `ok`。** git 不在 PATH 上、或者项目不在任何仓库里时，
我们**什么都没查出来**。`tracked` / `ignored` 这时候给的是 `null` 而不是 `false` ——
`false` 的意思是「我查过了，没被跟踪」，那在 git 不可用时是一句谎话。
界面上整页如实说明，不放任何绿色徽章。

## 5. 起子进程这条边界

这是继网络（阶段 3）之后的**第二个外部边界**，同样收敛在一个文件里
（`git/run.ts`），让「这个应用会执行什么外部程序」有一句话的答案。

- **`execFile` + 参数数组，绝不 `exec`。** `exec` 把命令交给 shell 解析，
  而我们要传的是用户项目里的文件路径 —— 那是用户能控制的内容。
- 🔴 **固定加 `-c core.fsmonitor=`。** git 会读**仓库本地**的 `.git/config`，
  而 `core.fsmonitor` 的值是一条会被 git 执行的命令。也就是说，在一个来路不明的
  仓库里跑任何 git 命令都可能执行仓库作者写的代码 —— 这是有记录的 RCE 向量，
  而这个应用恰恰是在**用户选的任意目录**里跑 git。命令行上的 `-c` 压过仓库配置。
- **`--no-optional-locks`**：只读检查不该往用户的仓库里写任何东西。
- **路径走 stdin 而不是 argv**：既躲开 ARG_MAX，也让以 `-` 开头的文件名
  不可能被当成选项。`ls-files` 那边用 `:(literal)` 前缀挡掉 pathspec 魔法。
- **不透传 git 的 stderr 和原始异常**：它们带着仓库路径和命令行。
  失败时由这一层自己构造一句话。
- **两条命令，不是每个文件两条。** 每个文件起两个进程，一个中等项目就是几十次 fork。

### 退出码 1 不是失败

`git check-ignore` 用退出码 1 表示「你问的这些路径一个都没被忽略」，
那是一个完全正常的答案。把它当成失败的话，一个**没有 .gitignore 的项目**
会整页显示「查不了」—— 而真实结论恰恰是「什么都没被忽略」，
也就是最该报警的那种项目。

所以 `run.ts` 不替调用方判断成败，只如实报出退出码。

## 6. 这个页面在 Vault 锁着的时候也能用

纳管文件的敏感度直接查 `config_entries.sensitivity` 那一列（它本来就不加密），
**全程不解密任何东西**。未纳管的文件走 `scanProject` 就地分类，只取计数。

于是安全检查不需要解锁 —— 而这恰恰是它最该能用的时候之一：
**你不需要打开保险柜，才能知道保险柜有没有被拍照传到 GitHub 上。**

报告类型 `FileRisk` 里**没有任何能放配置值的字段**，只有计数。
不是靠主进程自觉不填，是类型上就填不进去。

### 连未纳管的 .env* 也扫

用户在导入时取消勾选的 `.env.production` 不在库里，但它照样躺在磁盘上、
照样可能正被 Git 跟踪着。安全页只看已导入的那几个，等于只检查用户
已经在意的部分 —— 而漏掉的往往正是他没在意的那个。

## 7. 明确没做的：4b

`DEVELOPMENT_PLAN.md` §9 阶段 4 还剩后半段：

- **凭据版本、停用与轮换审计** —— 轮换本身在阶段 3 就做完了
  （换 Key + 状态退回未验证 + 预览并同步到全部绑定），4b 要补的是
  「旧版本标记 revoked」和不含明文的版本记录。
  影响范围预览就是现成的 `previewCredentialSync`，别另写一份。
- **剪贴板定时清理**（§7：默认 30 秒）。界面上现在还写着
  「自动清理将在阶段 4 接入」（`CredentialsView` 的 `copyKey`），做完记得改掉。
  打算顺手把复制整个挪进主进程：现在复制要先 `revealCredential` 把明文取到
  渲染层，而主进程自己就能写剪贴板 —— 挪过去之后**复制不再需要明文过桥**。
  清理时必须先确认剪贴板里还是我们写进去的那份，否则会把用户后来复制的
  东西一起清掉。

### 样例项目现在是一个真 Git 仓库

`buildGitFixture()` 起了真仓库，布置出四种状态：

```
.env.local                已跟踪 + 已忽略 + 有 Key   → critical（用 git add -f 造出来的）
apps/web/.env.production  未跟踪 + 未忽略 + 有凭据串  → critical
.env                      已跟踪 + 干净              → ok（不喊狼来了）
.env.example              已跟踪 + 模板 + 干净        → ok，且它是未纳管文件
```

拿假数据验这一层等于验了个寂寞：`check-ignore --no-index` 到底报不报已跟踪的
文件、退出码 1 是什么意思，都只有真 git 说了算。

改动前查过：**原有验收脚本里没有任何一条断言依赖 `gitRoot`**，
所以给样例项目 `git init` 不会弄红别的。`.git` 本来就在 `scan.ts` 的
`SKIP_DIRECTORIES` 里，遍历不会走进去。

### 🔴 位置很讲究：必须在任何东西改动样例文件之前跑

第一版把这一段放在脚本末尾，三条断言当场变红 —— 但**不是实现错了**：
那时 `.env` 已经被「以磁盘为准」那一步写进了一把 Key，`.env.staging` 也还
留着给界面验收用。断言测的是一堆残留状态，而不是刻意布置的那四种。

按 PHASE-1 §4 那条教训判断了一次「是我的期望写错了还是实现写错了」，
结论是前者，于是把整段挪到了「刚导入时所有文件都一致」那一句之后。

### 🔴 把 bug 放回去，两次都红了 —— 但第一次红得很说明问题

**摘掉 `--no-index`**：三条断言变红。值得记下来的是，
**`level === 'critical'` 那条并没有红** —— 因为 `.env.local` 里有高危值，
判定表第 3 条（已跟踪 + 高危值）照样把它兜成了 critical。

也就是说，如果当初只断言了等级，这个 bug 会完整地漏过去，
而受害的是另一种文件：**已跟踪 + 已忽略但暂时干净**的那种，
它会从 warning 静默掉到 ok。真正抓住它的是 `ignored === true`
和「理由里有没有那句话」这几条子断言。

这正是 PHASE-3 §7 那条教训的延续：**看的不能只是红没红，还得看红得对不对。**
