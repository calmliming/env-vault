## 2. 解析器：为什么不用 `Record<string, string>`

常见做法是把 `.env` 解析成键值对再序列化回去。那样注释、空行、顺序、引号风格、
行尾符全都没了，用户下次 `git diff` 会看到整个文件被重写。

`env/document.ts` 里每个节点都保留 `raw`（原始字节的精确切片）。写回时：

- 没改过的节点**原样吐出 `raw`**，逐字节相同；
- 改过的条目才用 `prefix + 编码后的值 + suffix` 重建。

「不改变无关格式」因此不是靠小心翼翼维护，而是结构上就不可能违反。

### 三处刻意的取舍

1. **行内注释必须有前导空白。** `FOO=bar # 说明` 里的 `#` 是注释，`FOO=pa#ss` 里的是值。
   dotenv 的某些实现在 `#` 处无条件截断 —— 那会把含 `#` 的密码悄悄切掉一半。
   对一个管密钥的工具来说这是数据损坏，不是风格问题。
2. **重复的 key 全部保留**，不去重。文件里真写了两遍就是两条记录；
   哪一条生效取决于加载它的运行时，去重等于替用户做决定。
   （这条直接导致了迁移 002：001 的唯一约束 `(env_file_id, key)` 和它冲突。）
3. **未闭合的引号降级成无引号值**而不是报错。半个文件解析失败对用户没有价值。

## 3. 敏感值的边界

```
磁盘 .env 明文
  → scan 解析
  → vault.encryptValue          （主进程内存，短暂）
  → SQLite BLOB                 （只有密文）
  → listEntries 掩码成占位符     🔴 明文到这里止步
  → IPC → 渲染层                （拿到的是 ••••••••）
```

明文过桥只发生在 `entries:reveal` 一个通道，且**每次调用都写一条操作记录**
（只记 key 名，不记值）。`verify-core` 有四条断言守着这个边界，其中一条直接去
数据库里翻 BLOB 确认没有明文片段。

Vault 锁定后 `listEntries` / `revealEntry` 直接返回 `VAULT_LOCKED`；
文件健康度不需要主密钥，所以仍然可读。

## 4. 验收脚本抓到的两个真 bug

这两个都不是测试写错，是实现写错：

### 4.1 重扫会推翻用户的取消勾选

`rescanProject` 有一条「自动纳管新发现的文件」，判断「新」的依据只是
「不在 `env_files` 里」。于是用户在导入时特意去掉勾选的 `.env.example`
会在下一次重扫时被收进来。

修法是**迁移 003**：导入时把没勾的文件记进 `project_exclusions`，重扫跳过它们。
真正新出现的文件（比如后来才创建的 `.env.staging`）仍然自动纳管 ——
用户已经把目录交给我们了，为每个新文件弹一次确认只会变成点掉不看的噪声。

### 4.2 `safeStorage` 跨进程解不开

界面验收要先播种数据再启动应用，两个进程。播种进程用 `app.setPath('userData', …)`，
应用用 `--user-data-dir` —— 结果应用解不开播种写的 `vault.key`。

两个原因叠在一起：

1. Windows 上 safeStorage 的 OSCrypt 密钥存在 userData 的 `Local State` 里，
   而那个文件的位置在 Chromium 启动早期就定了，`app.setPath` 发生得太晚，改不动它；
2. 播种脚本用 `app.exit()` 结束，进程立即终止，pref store 来不及把 `Local State` 落盘
   （实测沙箱里只有 `envvault.db` 和 `vault.key`，没有 `Local State`）。

修法：两个进程都走 `--user-data-dir`，且成功路径改用 `app.quit()` 走正常关闭流程。

> ⚠️ 这条对将来做**多进程/多实例**或者备份恢复有直接影响：
> `vault.key` 不是自包含的，它依赖同一个 userData 下的 `Local State`。
> 把 `vault.key` 单独拷到别处解不开。

## 5. 明确没做的：文件监听

计划 §9 阶段 1 的交付里有「文件哈希和**外部修改监听**」。哈希做了，
**常驻监听没做** —— 现在是「每次列表时比对哈希」的按需检测：

- 打开配置总览、切环境、点刷新时会算一次当前哈希，与入库时对比；
- 界面上能看到「有改动」「已丢失」，重扫能把新内容读进来；
- 但**文件在后台被改时界面不会自动亮起**，要等下一次读取。

没做的原因是常驻监听是个有状态子系统（chokidar 实例的生命周期、
去抖、重命名与原子写入产生的假事件、以及监听器和窗口关闭的对齐），
把它塞进这一刀会让本来已经很大的改动更难审。它和 §6.4 的
「导入文件 / 恢复中心记录」决策流程是同一件事，一起做更合理。

## 6. 命令

```bash
pnpm test         # 50 条单元测试（解析器 25 / 分类 15 / 扫描 10），node --test 原生跑 .ts
pnpm verify       # test + build + 核心验收 51 条 + 界面验收 37 条
pnpm verify:core  # 在真实 Electron 里跑数据库、Vault、扫描、导入、重扫
pnpm verify:ui    # 播种真实数据 → 启动真界面 → CDP 断言 → 截图
```

`verify:ui` 的数据来自 `verify:core --keep <沙箱>`：它先建库、创建 Vault、
导入一个刻意做得很难看的样例项目（CRLF、含 `#` 的密码、重复 key、多行值、
模板文件、node_modules 干扰项），然后保留沙箱给界面用。

这么绕一圈是因为「添加项目」要走系统目录对话框，CDP 点不动它。
与其为了测试在生产代码里开后门，不如让测试从数据那一侧进入 ——
界面因此是在**真实的锁定态**下启动的，第一件事就是走一遍解锁。

## 7. 阶段 0 的两个断言被改了

- **「配置表格渲染 6 行」→「解锁后表格自动填上真实变量」**：原来那 6 行是原型占位数据，
  现在数据来自数据库。
- **「滚动发生在内容区内部」**：原来靠「内容本来就比视口高」来验，
  那会随样例数据多少时灵时不灵 —— 一条断言只在数据够多时才有意义，
  等于在数据变少时静默失效。改成用 CDP 把视口压到 620px（`BrowserWindow` 的 `minHeight`）
  强制溢出。再矮就低于布局的设计下界，那种尺寸下的溢出属于人为制造。
