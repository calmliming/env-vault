## 2. 监听：为什么盯目录而不是盯文件

编辑器保存文件普遍是「写临时文件 → rename 覆盖」。直接监听文件路径的话，
rename 之后原来的句柄就失效了，监听器会**静默失效** —— 第一次保存能收到事件，
之后再改就再也收不到，而且不报任何错。监听父目录、按文件名过滤则不受影响。

去抖 300ms：一次保存常常触发多个事件（unlink + add，或 change 连发几次），
不去抖的话界面会闪几下。

监听层不做任何决策：它只回答「这个文件现在的哈希是什么」然后把事件抛出去。
渲染层收到后**只刷新状态，不改数据** —— §6.4 那句「任何外部修改在用户确认前
都不能被覆盖」反过来也成立：也不能在用户没确认时替他把中心记录改掉。

> ⚠️ 有**七处**操作会改变「有哪些文件 / 它们的基准哈希」：导入、移除、重扫、
> 以磁盘为准、以记录为准、编辑变量、删除变量。每一处都必须调
> `refreshWatchTargets()`。漏掉任何一处的后果是**静默的**：
> 监听器还活着，但拿旧哈希去比新文件。

## 3. 差异：按 (key, occurrence) 配对，不按行号

行号会因为上面插入一行注释而整体位移，那样一次无关的编辑会让所有变量看起来都变了。
按 key 配对则只有真正改了值的才亮起来。`occurrence` 必须参与配对，
否则 `DUP=first` / `DUP=second` 这种文件里的两条会互相顶掉。

**敏感项的差异两侧都是掩码。** 用户能看到「这一项变了」，看不到变成什么 ——
想看具体值要回配置表点「显示」，那条路径会留痕。差异面板是个一览视图，
把明文铺在上面等于绕过了 reveal 的审计。

## 4. 写回：四步原子替换

```
1. 并发校验（expectedHash）—— 见 §5
2. 备份原文件到 userData/backups/<路径哈希>/<时间戳>-<文件名>
3. 写同目录下的临时文件 + fsync
4. rename 覆盖目标
```

- 临时文件必须和目标**同目录**：跨设备 rename 会退化成复制+删除，就不原子了。
- 没有 fsync 的话 rename 可能先于数据落盘，掉电后得到一个长度正确但内容是零的文件。
- 备份不放原目录：`.env.bak-1234` 落在用户仓库里会被 `git status` 看见、
  可能被误提交、还会被下次扫描当成 `.env.*` 发现。
- 继承原文件的权限位：新建文件默认 `0o666&~umask`，会把原来 `0o600` 的 `.env` 放宽。
- 磁盘上不存在的 key **不追加**，原样报回去。静默追加会把中心记录里的陈旧变量
  塞回用户已经清理过的文件。

## 5. 这一刀里第一个值得记的 bug：守卫写成了摆设

`restoreFileFromCentral` 第一版是这样的：

```ts
const currentHash = currentFileHash(file.absolute_path)   // 现算
writeEnvFileAtomic(path, content, { expectedHash: currentHash })  // 拿来校验
```

看起来做了并发校验，实际上 `expectedHash` 永远等于当前值，**这个守卫不可能触发**。
验收脚本里那条「期间被外部改过就中止写入」因此一直是绿的 —— 它绿是因为
根本没进到判断，不是因为判断通过了。直到给它补上真正的并发场景
（先 diff、再从外部改文件、然后确认）才暴露出来。

修法是把 `expectedHash` 变成**调用方必须传入**的参数，语义是
「我这个决定是基于哪个版本做的」：

```
diffFile() → 返回 currentHash → 用户看着这份差异做决定 → restore(expectedHash=那个 hash)
```

主进程侧还加了一道：`expectedHash` 缺失或不是 64 位十六进制串直接拒绝，
不接受「没传就跳过校验」。

**教训**：一条从来没红过的断言，要么是代码真的对，要么是断言根本够不着它。
这两种情况在测试报告上长得一模一样。

## 6. 编辑与删除：三个决定

计划 §9 阶段 2 的交付里还有「搜索、筛选、**编辑**、**删除**、复制和掩码显示」。
搜索、筛选、复制、掩码在阶段 1 就有了，编辑和删除是这一刀补上的。
机器（`applyEdits` + 原子写入 + 备份 + 并发校验）本来就全在，
真正要定的是三件事：

### 6.1 改完立刻写盘，不攒着

另一条路是「只改中心记录，等用户点『同步到文件』」。它看起来和 §6.4 同形，
但有个硬伤：**drift 是靠哈希比对算出来的**。改中心记录不会让文件的哈希变，
于是界面会把一个实际上不一致的文件显示成「已同步」。要修就得引入一个
pending 标记（迁移 v4）和一整套新的状态语义 —— 而这些只是为了描述
一个本来可以不存在的中间态。

代价是多了一条前置约束：**文件有未处理的外部改动时不许就地编辑**。
这时候写下去等于替用户默默选了 §6.4 的方向。界面上按钮直接禁用并说明原因，
主进程侧独立再拦一道（`requireEditableEntry` 的守卫一）。

### 6.2 删除同时删掉文件里那一行

只删中心记录的话，下一次重扫或「以磁盘为准」会把它原样收回来 ——
**删除看起来自己撤销了自己**，这是最糟糕的一种结果。

`removeEntries` 和 `applyEdits` 共享同一个保证：没被点名的节点复用同一个
对象引用，所以除了消失的那一行，其余字节逐字不变。两处刻意的取舍：

- **相邻的注释不动。** `# 这个 key 是干嘛的` 属于上一行、下一行还是整段，
  只有写它的人知道，猜错就是替用户删掉他的笔记。
- **越界的 occurrence 报 missing，不像 `applyEdits` 那样夹到边界上。**
  改错一行还能改回来，删错一行是把用户的数据删了。

删掉重复 key 中的一条之后，**剩下几条在文件里的序号会整体前移**，
中心记录必须跟着重新编号，否则下次编辑那个 key 会按错误的序号去改另一行 ——
而且不报任何错。样例数据里的 `DUP` 因此从两条加到了三条：只有两条时，
`applyEdits` 对越界序号的「夹到边界」会碰巧命中正确的那一行，
**这个 bug 在两条的样本上是看不见的**。

### 6.3 敏感项默认盲写

点开编辑框**不等于**看见值：敏感项的输入框是空的，占位符写着「原值未显示」。
想看原值就点「显示」，那条路径已经留痕（§5.5）。已经显示过的直接预填。

于是「读明文」仍然只有 `entries:reveal` 一条路径，不新增审计语义、
也不开第二个读明文的口子。空输入框的保存按钮是禁用的 ——
空值在这里的含义是「还没输入」而不是「清空」；真要清空，先显示再删掉预填内容。

## 7. 这一刀里第二个值得记的 bug：明文一直躺在库里

`config_entries.original_format` 是一个**不加密的 TEXT 列**，而 `insertEntries`
往里写的是 `node.raw` —— 完整的原始行。也就是说从阶段 1 起，
每一条 `OPENAI_API_KEY=sk-proj-...` 的明文都直接存在数据库里。
HANDOFF §6 那条「SQLite BLOB（只有密文）」的边界，一直漏在这一列上。

为什么没被发现：验收里那条「🔴 明文不落库」只翻了 `encrypted_value` 一列。

```ts
// 它只看这一列，所以够不着 original_format
SELECT c.encrypted_value AS v FROM config_entries c ...
```

**又是 §5 那个形状**：断言是绿的，因为它根本到不了出问题的地方。
把泄漏放回去跑一遍，那条老断言依然 PASS，同时新断言报出
`泄漏的列: original_format` 和 `命中: sk-proj-, pa#ss, user:secret`。

修法两处：
1. 扫描侧改为产出**格式骨架**（`document.formatSkeleton`）—— 原始行里把值换成
   `<value>`，`export` 前缀、等号两侧空白、引号风格、行内注释全都还在，
   §4.2 要的「恢复引号、空格、注释关联」一样也没少，唯独没有值。
2. 迁移 004 把存量记录的这一列清空。清空而不是就地改写，是因为
   **这一列从来没有被任何代码读过** —— 写回走的是重新解析磁盘文件那条路。
   留着旧值只是继续留着明文。

配套的断言改成扫**整行的每一列**，外加直接搜数据库文件（含 `-wal`）的字节。
按列名扫而不是按字段名扫，是为了让将来新增的列自动落在断言范围内。

## 8. 验收

```
pnpm test         86 条单元测试（解析 25 / 分类 15 / 扫描 10 / 差异 11 / 写入 12 / 删除与骨架 13）
pnpm verify:core  94 条，真实 Electron 运行时
pnpm verify:ui    58 条，真界面 + CDP
```

界面验收里有一条是端到端的：脚本从**应用外部**改样例项目的 `.env`，
不点任何按钮，等界面自己把徽章变成「查看差异」—— 这条同时验证了
chokidar 监听、主进程推送、preload 的 on/off 桥、以及渲染层的订阅。
接着走完整个 §6.4 决策流程，确认中心记录真的更新了。

编辑与删除的界面验收**两头都看**：表格里的值，和 `.env` 文件里的字节。
只看表格的话，一个「改了记录没写盘」的实现也能骗过去。

两道并发守卫是**分别**验的，不是一起验的：

- 传**当前**磁盘哈希（并发校验必过）去编辑一个有外部改动的文件 → 只可能被
  「文件与记录不一致」拦下；
- 先把外部改动收进来（这道守卫必过）再传一个**过期**哈希 → 只可能被
  「你做决定时看到的不是这份内容」拦下。

分开验才能确认两道守卫各自可达。混在一起的话，第一道拦住就够了，
第二道有没有生效根本看不出来 —— 那又会变成一条够不着目标的绿断言。

> ⚠️ 界面验收里「解锁后表格自动填上真实变量」断言的是**键的集合**而不是行数。
> 行数只是个数字，verify-core 多做一步变更就得跟着改，失败时也只会告诉你
> "12 !== 14"，看不出少了谁。
