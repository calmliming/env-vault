## 2. 识别：值优先，名字兜底，冲突时不猜

和 `classify.ts` 的取舍一致：**值长得像某家的 Key 是最强的信号**，压过命名规则。

理由是「变量名没改、值换成了别家」在真实项目里非常常见 ——
`OPENAI_API_KEY` 里放一把 OpenRouter 的 Key 是标准做法。
按名字猜会**系统性地**猜错，而且错得很自信。

两个信号对不上时**两家都返回**，由用户在确认框里选。§6.2 本来就要求
「用户确认后创建模型凭据」，所以这里给的是排序，不是结论。

一个必须处理的细节：`sk-ant-` 同时符合 DeepSeek 的通用 `sk-` 规则。
所以形状分两档 —— 命中 `distinctiveKeyShapes`（独有前缀）就不再看
`genericKeyShapes`。反过来，裸 `sk-` 确实分不出 OpenAI 和 DeepSeek，
那就两家都报，让用户看变量名决定。

**自定义厂商永远不参与识别。** 没有任何形状能"认出"一个自定义厂商，
硬给它一条兜底规则的结果是每个认不出的 Key 都被贴上这个标签。

## 3. 🔴 适配器是纯函数，这一层不发网络请求

`describeValidation()` 只**描述**一次验证请求打哪个地址、带什么头，
真正发出去是另一层的事。这么拆有三个理由：

1. **验收脚本跑遍所有适配器也不会产生任何出站流量。** 一个管密钥的工具，
   测试时把用户的 Key 发到真实厂商去是不可接受的；
2. 「仅在用户显式点『验证』时才发」由调用方一处保证，
   而不是散在五个适配器里各自自觉；
3. 描述里带着 Key（在请求头里），调用方能在发之前决定要不要记日志。

验证一律打**元数据接口**（`/models` 这类），不打推理接口 ——
§7「验证请求使用厂商元数据接口，避免无意产生推理费用」。

Gemini 的 Key 走请求头而不是 `?key=`：URL 会被代理和服务端日志原样记下来。

## 4. 指纹：能比对，但反推不出 Key

```
fingerprint = HMAC-SHA256(从主密钥 HKDF 派生的子密钥, key) 取前 16 位十六进制
```

它只回答一个问题：**这两个地方用的是不是同一把 Key**。

为什么不直接 SHA-256：裸哈希意味着任何拿到数据库文件的人都能拿一份候选 Key
字典逐个哈希比对。API Key 熵很高，字典攻击本来就不现实 —— 但
「泄露的库 + 从别处拿到的一份 Key 列表」就能确认「这个人在用这把 Key」，
这个信息本身是敏感的。用派生子密钥之后，**只有库、没有系统密钥库就什么都验证不了**。

`vault.deriveSubkey(label)` 用 HKDF 做用途隔离，**不返回主密钥本身**，
也不该被改成那样。主密钥只在 `vault.ts` 里存在。

代价是指纹只能在解锁状态下算。这不构成限制：需要算指纹的时刻（新增、轮换）
本来就要加密 Key，一样得解锁。

## 5. 真源只能有一个

一个变量被提成凭据之后：

- **仍然留在配置表里**（§6.2 步骤 2、阶段 3 验收），来源照旧显示，
  另外标出它归哪条凭据管；
- **不能再就地编辑** —— 界面禁用入口并说明原因，主进程侧独立再拦一道
  （`keyBindingOf` + `updateEntryValue` 里的检查）；
- **仍然可以删除** —— 变量真的要没了是合理的，绑定会跟着一起解除。
  不连带解绑的话会留下一条指向已删变量的绑定，下次同步**静默少写一处**。

如果每一处还能各自改，那就是多个真源，必然分叉，而分叉之后
「这把 Key 到底是哪个」没有任何办法回答。凭据库存在的全部意义就是
「改一次，同步到多处」。

### 绑定按 (项目, 环境, 变量名) 配对，不按 entry id

重扫和「以磁盘为准」会**重建** `config_entries.id`。绑定指向 id 的话，
用户在编辑器里改一次文件、点一次「以磁盘为准」，所有绑定就全失效了 ——
而且不会有任何报错。按三元组配对则不受影响，验收里有一条专门守这个。

## 6. 验证请求：应用唯一的出站流量

§3 定的规矩全部落地了。这一层分成三个文件，边界是刻意的：

```
providers/index.ts     描述请求（打哪、带什么头）   纯函数，node --test 可跑
providers/validate.ts  发请求、把响应翻译成结论     纯函数 + 注入的传输，可跑
net/transport.ts       真的碰 socket               import electron，不可跑
```

拆成三层是为了让「谁会上网」有一个一句话的答案：只有 `net/transport.ts`。
前两层跑遍所有分支也不产生一个字节 —— 一个管密钥的工具，
测试时把用户的 Key 发到真实厂商去是不可接受的。

### 🔴 「验证失败」和「没验出结论」是两件事

这是整层最容易写错的地方，也是唯一一处会造成真实伤害的错误：

```
200      → valid    → status=active,  last_validated_at=now
401/403  → invalid  → status=invalid, last_validated_at=now
其余一切  → 没有结论 → 状态和验证时间一个都不动
```

网络不通、厂商 5xx、429 限流、404 地址错，说的都是「这次没问出答案」，
不是「你的 Key 坏了」。把它们当成证据的后果是：用户离线时点一次验证，
**所有凭据被标成失效** —— 而那正是他最需要这些 Key 的时候。

400 也归到「没结论」：有的厂商拿 400 回一切它不喜欢的请求，
包括我们自己把请求拼错的情况。判成 invalid 就成了因为本应用的 bug
去给用户的 Key 定罪。拿不准的一律往「没结论」放，这个方向上犯错是安全的。

判定收敛在 `validate.ts` 的 `isConclusive()` 一处。散开写的话，
将来加一个结论时必然漏掉其中一处，而且不会有任何报错。

### `invalid` 和 `revoked` 不能合并

新增的第四个状态是「已失效」（厂商拒绝），和「已停用」（用户自己按的）分开。
合成一个之后，界面上看到「已停用」再也回答不了「这是谁的决定」——
而这恰恰是用户下一步要做什么的依据：前者要去厂商控制台换一把，
后者自己按回去就行。`status` 列是无约束的 TEXT，加这个值不需要迁移。

配套的一条：**`active` 和 `invalid` 不在 `credentials:update` 的白名单里**
（`ipc/index.ts` 的 `USER_SETTABLE_STATUSES`）。它们是验证的结论，
只能由验证那条路写进去。允许渲染层手填，等于允许它在一个请求都没发的情况下
把凭据标成「可用」—— 那就是在假装做过实际没做的事。

轮换 Key 时状态退回 `unverified`，`last_validated_at` **一并清空**。
只退状态不清时间的话，界面上会出现「未验证」旁边挂着「验于 3 分钟前」，
而那句话说的是另一把 Key。

### 🔴 不跟随重定向

`net.fetch` 传的是 `redirect: 'error'`。fetch 规范只在跨源重定向时剥掉
`Authorization`，而 Anthropic 用 `x-api-key`、Gemini 用 `x-goog-api-key` ——
**自定义头不在剥离名单里**。也就是说一个配错的或被劫持的调用地址
只要回一个 302，就能把完整的 Key 收到任意主机去。调用地址是用户填的
（自定义厂商可以填任何 URL），所以这条必须堵死。
代价是正经的 301（http→https）也会失败并报「连不上」。

同一处还有两条：`credentials: 'omit'`（API 调用没理由带上应用 session 的 cookie）、
不读响应体（状态码足以得出结论，读进来只会平白多一份可能被打印的数据）。

### 🔴 异常不许逃出去

`runValidation` 的 `catch` **连 error 都不绑定**。

原因在 `ipc/index.ts` 的 `toFailure`：没认出来的异常会走
`console.error('[ipc] 未处理的异常', error)`，那是全应用唯一一处会把原始异常
整个打印出来的地方 —— 而这一层手里的 `request.headers` 装着完整的 Key。
让异常逃出去，等于把「请求头会不会进日志」托付给「传输层的 error 大概不会
带上请求头吧」这个假设。拿不到就不可能不小心传出去。

操作记录同理：只记厂商名、凭据名、结论和状态码。**连调用地址都不记** ——
自定义厂商的地址是用户填的，谁也不敢保证里面没有秘密。

### 🔴 测试安全网：`ENVVAULT_BLOCK_NETWORK`

验收全程注入假传输，但「记得注入」是一条靠自觉的规矩。它一旦被忘记，
后果是把测试用的 Key 发到真实厂商去 —— 而且测试照样绿，没有任何东西提醒你。

所以真传输那一侧留了一道见到 `ENVVAULT_BLOCK_NETWORK=1` 就拒发的拦。
`verify-core.ts` 在脚本开头设上它（写在脚本里而不是 npm script 里，
是为了不给跨平台的环境变量语法引入一个 `cross-env` 依赖），
`verify-ui.mjs` 给它 spawn 的 Electron 进程也带上。

界面验收因此可以**真的点一次那颗按钮**：它会走到「连不上」那条分支，
零出站流量，又正好落在最该守的那条断言上 —— 验证失败之后状态原地不动。

## 7. 验收

```
pnpm test         120 条单元测试（解析 25 / 分类 15 / 扫描 10 / 差异 11 / 写入 12 /
                                 删除与骨架 13 / 厂商适配器 20 / 验证执行层 14）
pnpm verify:core  149 条，真实 Electron 运行时
pnpm verify:ui    88 条，真界面 + CDP
```

### 两道并发守卫仍然是分开验的

和阶段 2 一样，同步的两道守卫必须各自可达，否则第一道拦住就够了，
第二道有没有生效根本看不出来：

- 传**当前**磁盘哈希去同步一个有外部改动的文件 → 只可能被「文件与记录不一致」拦下；
- 先把外部改动收进来（这道守卫必过）再传一个**过期**哈希 →
  只可能被「你查看预览之后文件又被改动」拦下。

### 逐个目标报告，不是全有或全无

跨多个文件的写入没法原子回滚。验收里专门造了「一好一坏」的场景：
一条正常绑定加一条指向不存在变量的绑定一起同步，
**好的必须写进去、坏的必须单独报错**。谎称"整体失败"会让用户以为
第一个文件没被改，而它已经改了。

### 「没结论不改状态」那条断言差点够不着它要守的分支

写完之后按惯例把 bug 放回去跑了一遍（去掉 `if (conclusive)` 这道条件），
四个用例里只红了三个 —— **「连不上」那条没红**。

原因是那一组当时从 `invalid` 状态起步：错误的写入正好也写 `invalid`，
而 `last_validated_at` 又落在同一毫秒里，于是「改了」和「没改」长得一模一样。
改成先验回 `active` 再跑这一组之后，任何错误写入都会把状态翻成 `invalid`，
四条全部可达。顺带这也是更真实的场景：昨天验过是可用的，今天离线点一次。

这正是 §8 那条教训的又一次应验 —— 断言绿着，但它够不着。

### 样例数据里为什么多一个 `ANTHROPIC_API_KEY`

阶段 3 的绑定、同步、轮换、删除都拿这一条练手。不复用 `OPENAI_API_KEY`
是因为同步会**覆盖它的值**，而界面验收还要靠那把 Key 验
「没点显示就不给明文」—— 两边抢同一个样本，先跑的那个会把后跑的弄红。

> ⚠️ `pnpm verify:ui` 跑的是 `out/verify/index.mjs` 这个**已构建**的产物，
> 而它由 `verify:core` 那一步的 esbuild 生成。只改了 `verify-core.ts` 就直接跑
> `verify:ui`，用的还是旧包 —— 会看到一堆对不上的失败。`pnpm verify` 顺序是对的。
