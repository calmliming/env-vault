# 阶段 5b：从模板生成 `.env.example`

对应 `DEVELOPMENT_PLAN.md` §9「阶段 5」的第二项。

前置记录：[PHASE-0.md](PHASE-0.md) ~ [PHASE-5A.md](PHASE-5A.md)。

## 1. 这一刀交付了什么

| 内容 | 状态 | 落在哪 |
| --- | --- | --- |
| 生成不含值的模板（保注释、顺序、引号风格） | ✅ | `src/main/env/template.ts`，22 条单元测试 |
| 注释里的赋值一并脱敏 | ✅ | `redactCommentText`，整行与行内共用 |
| 🔴 高敏值兜底检查，没过就拒绝写盘 | ✅ | `findLeaks` + `db/template.ts` |
| 预览 → 二次确认 → 原子写 + 备份 | ✅ | `modals/TemplateModal.tsx` |
| 批量导入与加密导出 | ⬜ 5c | 见 §7 |

**5b 只做模板生成。** 规格 §12 原本把「`.env.example` 生成、批量导入、加密导出」
放在一起，拆开的理由和阶段 4 拆成 4a/4b 一样：导出是**第五条明文出口**，
它的边界值得单独一刀想清楚，而模板生成本身也不是小活（见 §3）。

## 2. 为什么它和前面几刀都不一样

前面四条外部边界（出站流量、执行外部程序、系统剪贴板、把 Key 交给子进程）
都是「值离开本进程」。模板是第一个**设计上就要被提交进 Git** 的产物 ——
值离开本机、进入版本库、可能进入公开仓库。正是阶段 4a 整套安全检查存在的理由。

所以这里的默认一律取保守的那一边：读不懂的行宁可略去，也不赌它不含值。

**顺带一个好性质：这条路全程不解密。** 源头是磁盘上的 `.env` 文件而不是中心记录
（中心记录里根本没存注释，而模板的价值有一大半在注释上），所以不需要主密钥，
**Vault 锁着也能生成**。和 `db/security.ts` 同一个性质，验收里有一条断言专门守着
——它是在 `vault.lock()` **之后**跑的。别"顺手"给它加上 `requireUnlocked()`。

## 3. 🔴 最自然的写法会把明文写进 Git

`# OPENAI_API_KEY=sk-proj-…` 这种被注释掉的旧 Key，`parseEnv` 解析成
`comment` 节点，`raw` 里是**整行原文**。而 `formatSkeleton` 只作用于 `entry` 节点。

于是「把每个 entry 的值换成占位符、注释原样保留」—— 这个最自然、也最符合
「保格式」传统的写法 —— 会把注释里的明文 Key 直接写进模板。
行内注释（`EntryNode.suffix`）走同一条路，**只堵整行等于只堵了一半**。

更麻烦的是**现成的安全网接不住它**：`risk.test.ts` 有一条「模板里塞了真 Key
依然是 critical」，但它靠 `FileRisk.highCount`，而 `highCount` 只数 entry 节点
（`security.ts`）。注释里的 Key 不是 entry → `highCount` 为 0 → 安全检查页照样判 `ok`。
一个泄漏同时躲过了生成和检查两道。所以断言必须自己扫生成结果。

### 脱敏规矩：像赋值的擦掉，其余原样

`redactCommentText` 定位 `#`，然后从正文的每个「词首」试一次 `parseEnv`，
命中一条赋值就把值抹掉。

**第一版要求整段注释正文恰好是一条赋值，`# 旧的 KEY=…` 直接漏过去** ——
而赋值前面带一段散文（`# 旧的 KEY=…`、`# old KEY=…`）恰恰是最常见的写法。
现在从每个词首试，`## KEY=…` 这类多重注释也一并覆盖了。

用**真正的解析器**判断而不是在这里另抄一份赋值正则：抄一份就意味着
`document.ts` 的解析规则改了这里不会跟着改。

已知的过度脱敏：`# note=see docs` 这种带等号的散文也会被当成赋值，变成 `# note=`。
我们分不出「被注释掉的配置」和「碰巧带等号的说明」，而目的地是 Git ——
宁可多擦掉一句说明。有一条用例把这个取舍钉住了，它不是在描述 bug。

## 4. 🔴 检测有缝，所以后面还有一道结构性兜底

「像不像赋值」是形状判断，必然漏。`# TODO: set API_KEY=sk-real` 里 `TODO`
后面是冒号不是等号，不匹配赋值形状，原样留下。

所以生成完再反过来查一遍：源文件里那些敏感值，有没有哪个还能在结果里搜到。
**命中就拒绝写盘**，并只报行号和 key 名 —— 值本身一个字符都不进错误信息。

只查 `high`（值本身长得像凭据）外加**长度 ≥ 16 的 `sensitive`**（靠名字判出来的）。
不全量比对，是因为值为 `true` / `jwt` 这种短词的变量，它的值本来就会出现在
`# 默认 true`、`# 支持 jwt 和 session` 这类注释里 —— 全量比对会把一份完全正常的
模板判成泄漏，而**一条会误报的断言用两次就没人看了**（HANDOFF §8）。

这和 5a 的「前后快照而非白名单」是同一个取向：用一个能直接回答问题的机制，
而不是一张会越加越长的例外表。

> ⚠️ 诚实的残留：注释里若是一把**已经不在文件里的旧 Key**，兜底也够不着它 ——
> 它不在「源文件当前的值」这个集合里。界面上的提示和这里都直说，不假装覆盖全。

## 5. 写盘：复用现成的原子写，但要处理「文件本来不存在」

目标是**源文件同目录**下的 `.env.example`（源文件可能是 `apps/web/.env.production`，
那份模板属于 `apps/web/`）。

- 目标已存在 → `writeGuarded`，自带备份到 userData + fsync + rename。
- 目标不存在 → `openSync(path, 'wx')` **独占创建**，再走同一条原子写。

`expectedTargetHash` 为 `null` 的语义是**断言**「我预览的时候它不存在」，
**不是**「跳过校验」。兑现这个断言的是那个 `'wx'`，不是 `existsSync` ——
后者到写入之间有一个竞态窗口。

IPC 层为此加了 `asFileHashOrAbsent`，与现有的 `asFileHash` 并列。
**没有把 `asFileHash` 改成接受空值**：它的注释点名拒绝空值，而那三条写盘路径
（写回、编辑、删除）的目标一定是已存在的文件，它们没有「文件不存在」这种合法情形。

创建那条路上**不传 expectedHash**：目标刚由我们独占创建，拿现算的哈希去比现算的
哈希永远不可能触发（PHASE-2 §5 那条教训）。写一个假守卫比不写更糟。

## 6. 内容由主进程重新生成，渲染层送不进来

`template:write` 的请求里**没有 content**，只有 `fileId` 和目标哈希。

接受渲染层送来的内容，等于给它开一个「往任意 `.env.example` 写任意字节」的原语，
而渲染层是加载页面内容的地方。预览里那份文本只是拿去显示的。

界面这一侧对应的规矩：兜底没过就**根本不给按钮**，不是弹个警告让人点掉。

## 7. 明确没做的

- **批量导入与加密导出**（5c）。计划 §7：导出要二次确认、优先导出加密包。
  前置结论已经定了：**加密导出用用户口令 + KDF**，不是系统密钥库派生 ——
  密钥库派生出来的包只有本机能解，而「换机器 / 备份」正是导出的用途。
- **1Password / Bitwarden / Doppler 适配**。需要机器上装有各自的 CLI，
  验收里只能全程用假的，而一个只验过假实现的集成等于没验。先想清楚怎么验。
- **逐变量勾选「哪些进模板」**。`.env.example` 的惯例就是所有 key 都列出来，
  漏一个反而坑人，而「漏选了某个 key」这种错误是静默的。

## 8. 验收

```
pnpm test         201 条单元测试（新增：模板生成 22；200 通过 + 1 条按平台跳过）
pnpm verify:core  200 条（新增 13）
pnpm verify:ui    121 条（新增 8）
```

### 三次「把 bug 放回去」，三次都红得对

| 放回去的 bug | 应该红的 | 实测 |
| --- | --- | --- |
| `comment` 节点不脱敏 | 整行注释那三条 | ✅ 红 3 条 |
| `suffix` 不脱敏 | 行内注释那条 | ✅ 红 1 条 |
| 兜底把子串匹配写成相等比较 | 兜底那四条 + 集成两条 | ✅ 单元红 4、核心红 2 |

第三次特意挑了一个**不产生未使用变量**的改法（`includes` 改成 `===`），
并且先确认 `pnpm build` 真的成功了才去跑 `verify:core` ——
5a 那次空过的实验就是栽在「改动让构建失败、验的还是旧产物」上（HANDOFF §8）。
核心那条红出来的 detail 是「拒绝信息=（居然没拒绝） / 目标文件存在=true」：
带泄漏的模板真的被写到磁盘上了，正是它要守的分支。

### 🔴 两条差点空过的断言

**一、界面写出来的文件。** 第一版是「点确认 → 读磁盘 → 搜不到明文」。
但 `verify:core` 已经用同一个底本生成过一次了 —— 界面就算根本没写成功，
磁盘上也躺着一份长得一模一样的旧结果，断言照样绿。
改成先从 node 侧把目标涂成一段哨兵，再让界面写，然后确认哨兵被覆盖了。

**二、界面测试的底本。** 弹窗默认挑 `.env`，而 fixture 的 `.env` 里本来就没有秘密 ——
拿它去验「模板里没有明文」同样是空过的。改成在界面里把下拉切到 `.env.local`
（密钥密布的那份）再生成。

两条都是同一个形状：**断言够不着它要守的分支时，看起来和真的通过一模一样。**

### 顺带修掉的一条既有断言

`verify:ui` 的「记录里的动作都是中文」原本用「标签里不含 `.`」当代理，
被新标签「生成 .env.example」撞红了 —— 那是个合法标签，只是里面有文件名。
断言的名字说的是「都是中文」，就直接验这个：每个标签至少含一个汉字。
`template.generate` 这种漏出来的原始标识依然会红，合法标签不再误伤。
**代理条件比它要守的性质宽，早晚会误伤到一个合法的新写法。**

### `preload 只暴露白名单方法` 那条按预期红了一次

38 → 40（`previewTemplate` / `writeTemplate`）。数字写死是有意的：
桥上多一个方法就红一次，逼人过一眼那是不是该暴露的东西。
